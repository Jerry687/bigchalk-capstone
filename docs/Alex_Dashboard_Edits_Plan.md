Upload (`.xlsx`/`.csv`) → each (product, channel) group written to the default or the override; **variables not listed for a group become excluded** (completes V3's template rule). **Failure-safe (2nd + 3rd review):** the upload is **atomic** end-to-end. If a commit fails, **roll back** (restore originals, remove new targets); if a restore *itself* fails, it reports **`ROLLBACK INCOMPLETE`**, **preserves the backup** (never deletes the last original), and returns a **three-state result** (`applied` / `rejected` / `rollback_incomplete`). The callback bumps `config_rev` (refresh) on `applied` **and** `rollback_incomplete` (disk changed — shows `⚠ PARTIAL WRITE` + `.bak` recovery path); only `rejected` leaves state untouched. **All config mutations** — default creation (in `capstone_pipeline`), Save/Run persist, Regenerate, Reset, and the upload commit — share **one** `_CFG_WRITE_LOCK` (RLock, in `capstone_pipeline`). *(os.replace is per-file atomic; lock covers in-process concurrency — cross-process would need OS file locks.)* `apply_template_df` returns a structured `ok`, so a rejected upload never bumps `config_rev`. Verified: typo / bad-channel / duplicate / partial-validation-failure / empty / mid-write-failure all write nothing and leave no temp files; valid single- and multi-group uploads apply.

## Open decisions (need Alex / team)

- **Config granularity — RESOLVED (Jerry): two-tier model, Group 5.5 (core done).** Product **default** + optional Product × **Channel override**; resolution **override > default**. Editor CONFIG scope selector (Product default / This channel) + status line; Save & Variables-Run write the scoped file; **Regenerate** and a new **Reset to default** (delete override) both act on the current scope; the web batch resolves per channel. Files: `varconfig_<ds>_<brand>.csv` / `…__ch_<channel>.csv`.
  - **Runtime is NOT uniformly "override wins" (review clarification).** A Variables-tab **Run is WYSIWYG** — it runs the exact file you're editing (default *or* override). The **Batch and other runners use override-wins resolution**. So editing the default and Running from Variables can differ from what the Batch does for a channel that has an override — by design.
  - **Write→read race — FIXED, and writer set now complete.** Save / Regenerate / Reset formerly fanned out to independent callbacks with no ordering guarantee (a reader could re-read disk *before* the write). Now a single `config_rev` signal is bumped by the writer **after** touching disk, and the table + scope-status readers depend on `config_rev` (not raw clicks) — Dash's graph enforces write-then-read. **All four writers bump it:** Save, Regenerate, Reset, **and a Variables-tab Run** (which also persists) — the last closes the "config saved but model failed" gap where the scope status could stay stale. Writers bump only on a real change (`no_update` on no-op/invalid). *(Side note: `run_model` moved to `prevent_initial_call=True` to allow the duplicate `config_rev` output; effect is only that Diagnostics starts empty until the first Run instead of showing a "load a datafile" hint.)*
  - **CLI runners unified (review #2) — DONE.** Resolver + default-creation live in `capstone_pipeline` (`resolve_config_path`, `generate_default_config`, `load_or_create_default_config`) as the single source of truth; `dashboard.py` delegates to them. **`run_all.py`** resolves per (brand, channel), creating the default if missing. **`run_brand1_channel1.py`** resolves the tiered config and creates the default when none exists.
  - **ACV force + legacy fallback (2nd review) — DONE.** `run_all.py` **no longer sets `force_include=["ACV …"]`** — ACV force lives solely in the config's **role**, so an analyst editing ACV to `auto` is honored identically by CLI and web app (verified: `role=auto` ⇒ not forced in the CLI run; `role=force` ⇒ forced). The **legacy root `variable_config.csv` fallback is deprecated**; the single-slice runner now creates the tiered default instead. `run_all.py` docstring corrected (ACV forced *by default via role*, not hard-forced).
  - **Single creation path (3rd review) — DONE.** `dashboard.load_or_create_config` now **delegates to `cp.load_or_create_default_config`** instead of writing the default itself — so there is exactly one place that creates a default config for app + CLI (verified: deleting the default and reloading recreates it through the shared entry; dashboard no longer calls `to_csv` for it). Generation (`generate_default_config`, ACV-force) is also single-source.
